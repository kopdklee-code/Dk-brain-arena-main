# DK BRAIN ARENA — 1차 구현 지시문
# 목표: 공통 플랫폼과 게임별 독립 배포 구조 검증

현재 작업 폴더에서 DK BRAIN ARENA의 1차 구현을 진행해 줘. 기획 설명만 하고 끝내지 말고, 아래 범위의 파일 작성·실행·검증·문서화까지 진행해 줘. 이 지시문은 이전 대화 없이도 적용할 수 있는 작업 기준이다.

## 1. 확정된 프로젝트 기준

- 플랫폼 이름은 DK BRAIN ARENA다.
- 화면은 HTML, CSS, 순수 JavaScript로 구현한다.
- 데이터베이스와 웹 호스팅은 Firebase를 사용한다.
- 플랫폼에 게임을 하나씩 추가하는 방식으로 개발한다.
- 각 게임은 개별 파일 상품으로도 판매할 수 있어야 한다.
- 게임 규칙·화면의 원본은 하나로 유지하고, 플랫폼용과 판매용을 생성한다.
- 플랫폼판과 판매판을 복사한 뒤 서로 다른 코드로 관리하지 않는다.
- React, Vue, Next.js, TypeScript, Tailwind를 새로 도입하지 않는다. CSS는 직접 작성한다.
- Firebase SDK, Firebase CLI, 검증·패키징에 필요한 최소 개발 도구는 사용할 수 있다. 개발 도구 사용과 서비스의 기술 스택을 구분한다.
- 기존 합의와 사용자 지시를 임의로 변경하지 않는다.

## 2. 작업 전 확인과 기본 선택

먼저 현재 폴더의 파일, 적용되는 AGENTS.md·CLAUDE.md, package.json, Firebase 설정, Git 변경 상태를 확인한다. 비밀값을 출력하지 않는다. 기존 프로젝트와 사용자 변경을 보존한다.

DK BRAIN ARENA와 무관한 프로젝트가 있으면 해당 코드를 덮어쓰지 말고 별도 작업 디렉터리를 만든다. 관련 기존 프로젝트가 있으면 그 구조에서 필요한 부분을 확장한다.

신규 프로젝트에서 아직 정해지지 않은 항목은 아래 기본값을 적용하고 docs/PROJECT_SPEC.md에 ‘구현 기본값’으로 기록한다. 사용자가 직접 확정한 사항과 구분한다.

- 데이터베이스: Cloud Firestore.
- 사용자 식별: Firebase Authentication.
- 서버에서 검증할 게임 행동과 점수: JavaScript로 작성한 Cloud Functions.
- 유료 파일 보관과 구매자 다운로드: 후속 단계에서 Cloud Storage와 구매 권한 검증으로 구현.
- 기존 프로젝트가 이미 Realtime Database를 사용하면 자동으로 이전하지 말고, 기존 구성을 유지할 수 있는지 먼저 판단한다.
- 초기에는 Firestore와 Realtime Database를 함께 도입하지 않는다.

확인 결과와 구현 순서를 짧게 알린 뒤, 되돌릴 수 있는 로컬 구현은 계속 진행한다. 사소한 선택마다 승인을 요구하지 않는다. 해결할 수 없는 실제 충돌이나 접근 제한은 정확히 설명한다.

이번 작업 범위는 로컬 구현과 에뮬레이터 검증이다. 원격 배포, Git 원격 푸시, 실서비스 데이터 변경, 새 클라우드 프로젝트 생성, 요금제 변경은 포함하지 않는다. 배포 설정과 실행 안내는 준비한다.

## 3. 이번 단계의 완료 범위

아직 첫 상용 게임은 선정하지 않았다. 임의로 상용 게임을 확정하지 않는다. 아래 공통 기능과 개발 검증용 샘플 하나를 만든다.

1) 플랫폼 홈·게임 목록·게임 상세
2) 진행자 방 생성·게임 시작·라운드 마감·결과 확인
3) 참가자의 입장 코드·닉네임 입력과 참가 화면
4) 빔프로젝터 등에서 사용할 공개 화면
5) 검증용 샘플 게임 하나
6) 같은 샘플 원본에서 생성하는 오프라인 실행 HTML과 ZIP
7) 실제 로컬 실행 방법과 검증 결과 문서

게임 목록에는 구현된 샘플만 표시한다. 가상의 출시 게임·구매자 수·성공 사례를 넣지 않는다. 실제 판매, 결제, 구독, 토너먼트, 기관 관리, AI 분석, 자체 게임 편집기는 이번에 구현하지 않는다.

## 4. 공통 구조와 게임 모듈

게임 모듈은 플랫폼의 로그인·결제·특정 데이터베이스에 직접 의존하지 않게 한다.

각 게임의 기본 구성:
- manifest.json: gameId, 제목, 설명, gameVersion, 지원 인원, 지원 화면·배포 방식, isDemo.
- rules.js: 초기 상태, 행동 검증, 상태 변경, 점수·종료 조건.
- view.js: 상태를 HTML 화면에 표시하고 입력을 전달.
- game.css: 해당 게임 범위에만 적용되는 스타일.
- assets/: 해당 게임의 자료.
- 운영·실행 안내.

최소 공통 계약:
- createGame: 초기 상태 생성.
- executeAction: 행동의 적합성 확인과 상태 변경.
- getView: 보는 사람에게 허용된 정보 생성.
- getResult: 종료 결과 생성.

규칙 코드는 DOM·Firebase SDK·네트워크·브라우저 저장소를 직접 호출하지 않는다. 시간이나 난수가 필요하면 외부에서 값을 전달받는다. 샘플은 난수를 사용하지 않아도 된다.

플랫폼의 대기·진행·종료 상태와 게임 내부의 세부 단계를 구분한다. 특정 게임의 라운드나 점수 공식을 공통 코드에 고정하지 않는다.

Firebase 연결부와 로컬 실행 연결부는 같은 게임 계약을 제공한다. 온라인판은 서버 판정 결과를 받아 표시하고, 오프라인판은 같은 규칙 원본을 브라우저 안에서 실행한다.

초기에는 검증된 게임을 코드의 등록 목록에 추가하는 방식으로 충분하다. 임의 JavaScript 업로드 실행이나 범용 플러그인 마켓은 만들지 않는다.

권장 영역:
- src/platform/
- src/shared/
- src/games/<gameId>/
- src/adapters/
- functions/
- scripts/
- tests/
- docs/

파일명과 세부 디렉터리는 기존 구조에 맞춰 조정해도 되지만, 위 역할의 경계는 유지한다.

## 5. 검증용 샘플의 정확한 규칙

이름은 ‘숫자 선택 샘플’, ID는 demo-number-choice, isDemo는 true로 둔다. 화면에 ‘개발 검증용’이라고 표시하며 판매 게임으로 소개하지 않는다.

- 샘플은 플레이어 2명, 총 3라운드로 구성한다. 이 값은 플랫폼 전체의 제한이 아니다.
- 각 플레이어는 라운드마다 1·2·3 중 하나를 한 번 제출한다.
- 제출된 선택은 공개 정보다.
- 진행자가 라운드를 마감하면 각자 선택한 숫자만큼 점수를 받는다.
- 미제출자는 그 라운드에서 0점을 받는다.
- 같은 제출과 라운드 마감이 반복되어도 점수는 한 번만 반영한다.
- 마지막 라운드 이후 누적 점수로 결과를 표시하고, 동점은 공동 순위로 처리한다.
- 시작 이후 신규 플레이어 입장은 막고 기존 참가자의 재접속은 허용한다.
- 이번 샘플의 라운드 마감은 진행자가 수동으로 실행한다. 정밀한 자동 마감 시스템은 이번 범위에 넣지 않는다.

온라인판은 진행자와 참가자들이 각각 접속한다.
오프라인판은 한 PC에서 진행자가 두 플레이어의 선택을 입력한다.
두 방식의 입력 주체와 연결 방식은 다르지만, 같은 선택·마감 순서를 입력하면 같은 결과가 나와야 한다.

## 6. Firebase 구현 기준

- 로컬에서는 Firebase Emulator Suite의 Auth·Firestore·Functions·Hosting을 사용한다.
- 에뮬레이터 설정이 없거나 연결에 실패했을 때 실서비스로 자동 연결하지 않는다.
- 진행자 식별과 참가자 식별을 구현한다. 참가자는 익명 인증 UID와 닉네임을 분리해서 관리한다.
- 로컬 검증용 진행자 계정 또는 에뮬레이터용 인증 방법을 제공한다. 실제 외부 로그인 설정이 없어도 검증할 수 있게 한다.
- 방 소유자는 해당 방의 진행자다. 방 진행 권한을 플랫폼 전체 관리자 권한으로 확대하지 않는다.
- 입장 코드는 방에 참가하는 수단이며 관리자 권한으로 사용하지 않는다.
- 참가자가 방 상태·다른 사람의 정보·최종 점수를 직접 덮어쓸 수 없게 한다.
- 공개 상태, 참가자 정보, 개인별 비공개 상태, 서버 전용 상태를 문서 단위로 분리할 수 있는 구조를 둔다.
- 샘플에 없는 비공개 게임 기능까지 구현하지는 않되, 공개 문서에 비밀값을 넣고 CSS로 가리는 구조는 만들지 않는다.
- Functions에서도 사용자 UID·방 소유자·참가자 여부·현재 단계·입력을 검증한다. SDK나 보안 규칙이 이 검증을 대신한다고 가정하지 않는다.
- 동시 요청과 중복 요청으로 점수가 바뀌지 않도록 요청 식별자·트랜잭션 등 적절한 방법을 적용한다.
- Firestore 트랜잭션이 재시도되어도 외부 부수효과나 추가 점수가 발생하지 않게 한다.
- 시작 시 gameId·gameVersion·설정을 고정하고 진행 중인 방에 새 규칙을 섞지 않는다.
- 참가 화면에서 나갈 때 불필요한 실시간 구독을 해제한다.
- 서버 전체 상태를 브라우저로 보내지 않는다. 사용자별로 허용된 정보만 전달한다.

Cloud Functions 배포 묶음에는 필요한 공통 규칙 코드가 실제로 포함되어야 한다. 저장소 다른 위치의 파일을 상대경로로 참조해 로컬에서만 동작하는 상태를 완료로 보지 않는다. 게임 규칙의 원본은 하나이며, 배포 시 그 원본으로 필요한 산출물을 생성한다. 에뮬레이터도 실제 배포 대상으로 구성한 Functions 묶음을 사용한다.

Functions를 운영 환경에 배포할 때 필요한 Firebase 요금제 등 외부 설정은 README에 설명하되, 이번 작업에서 계정·요금제를 변경하지 않는다.

## 7. 독립 판매를 위한 패키징 검증

이번에는 검증용 샘플의 오프라인 패키지를 만든다. 기본 사용 대상은 PC 브라우저다.

- 같은 규칙·화면 원본으로 standalone.html을 생성한다.
- 필요한 JavaScript·CSS·자료를 포함하고 CDN·Firebase·외부 폰트 없이 실행한다.
- 생성된 HTML은 파일을 더블클릭해 file://로 열고 인터넷 연결 없이 실행할 수 있어야 한다.
- 플랫폼의 여러 ES module 파일을 그대로 복사하는 것으로 이 요구가 충족되었다고 보지 않는다.
- 진행 초기화와 최종 결과 확인을 지원한다. 결과 내보내기는 가능한 간단한 파일 형식으로 제공한다.
- ZIP에는 standalone.html, 빠른 시작 안내, 버전·실행 조건을 포함한다.
- 샘플 ZIP에는 개발 검증용이며 판매 상품이 아니라는 표시를 한다. 최종 상업용 라이선스 조건을 임의로 확정하지 않는다.
- 다른 게임, 운영 비밀키, 구매자 데이터, 플랫폼 관리 기능을 포함하지 않는다.
- 판매용 패키지를 Hosting의 공개 디렉터리에 자동 배포하지 않는다.
- 신규 구성의 기본 출력 위치는 Hosting 공개 파일 dist/hosting, 판매용 파일 dist/packages로 분리한다. firebase.json의 Hosting 공개 경로에는 dist/hosting만 지정한다. 기존 구조에서는 같은 분리 원칙을 적용한다.
- 생성된 HTML이나 규칙 사본을 직접 수정하지 않고 원본을 수정한 뒤 다시 생성한다.
- 오프라인 샘플에 QR 기반 다기기 접속 기능이 있다고 표시하지 않는다.

향후 실제 게임은 ‘오프라인 실행형’ 또는 ‘구매자 Firebase 설치형’ 등 지원 가능한 배포 방식을 선언한다. 구매자 Firebase 설치형에는 해당 게임의 Hosting 파일뿐 아니라 필요한 Functions·보안 규칙·설정·안내도 포함해야 한다. 이 설치형 전체 구현은 이번 범위 밖이다.

## 8. 화면 기준

- 한국어 UI, PC 진행자 화면과 모바일 참가자 화면을 구분한다.
- 공통 색상·여백·글자 크기는 CSS 변수로 관리한다.
- 운영자가 현재 단계·참가 상태·제출 상태·결과를 쉽게 구분할 수 있게 한다.
- 연결 중·제출 중·실패·재접속 상태를 사용자에게 정확히 알린다.
- 키보드로 주요 버튼을 사용할 수 있게 하고 색상만으로 상태를 구분하지 않는다.
- 디자인은 간결하게 하고 게임을 끝까지 실행하는 흐름을 우선 완성한다.

## 9. 실행 확인과 완료 기준

구현 후 의미 있는 검증을 실제로 실행하고, 실패 원인을 고친 뒤 해당 검증을 다시 수행한다.

필수 확인:
1) 서로 다른 인증 상태의 참가자 2명과 진행자로 방 생성·참가·3라운드·결과까지 진행.
2) 참가자 새로고침·재접속 후 자신의 자리와 현재 상태 복구.
3) 중복 제출·반복 마감·이미 지난 라운드 제출의 처리.
4) 다른 참가자의 데이터 변경과 진행자 전용 명령 거부.
5) 비공개·서버 전용 문서에 대한 권한 없는 읽기 거부. 필요하면 테스트 전용 데이터를 사용.
6) 동일 초기 상태와 행동 순서에서 온라인 판정과 로컬 판정의 최종 결과 일치.
7) 생성한 standalone.html을 file://와 네트워크 차단 조건에서 실행하고 3라운드 완료.
8) 새 작업 디렉터리에서도 Functions 묶음의 규칙 모듈이 누락되지 않음을 확인.
9) Hosting 산출물과 판매 패키지의 내용이 분리되어 있는지 확인.

실제로 실행하지 못한 항목을 통과로 표시하지 않는다. 브라우저·에뮬레이터·의존성 설치 등의 제약이 있으면 완료한 구현, 실행한 확인, 미확인 항목을 나눠 보고한다. 접근·권한 제한을 우회하거나 기존 설정을 무력화하지 않는다.

현재 범위 밖의 기능을 만들기 위해 검증 범위를 계속 늘리지 않는다.

## 10. 문서와 최종 보고

기존 파일이 있으면 내용을 보존하며 필요한 부분을 반영한다.

- CLAUDE.md: 확정된 기술·구조 원칙, 작업 범위 기준, 실행·검증 명령, 관련 문서 위치를 간결하게 기록한다.
- docs/PROJECT_SPEC.md: 사용자 확정 사항, 구현 기본값, 모듈 구조, 이번 범위와 후속 범위를 구분한다.
- docs/GAME_MODULE_GUIDE.md: 다음 게임을 추가하는 방법과 배포 방식 선언 규칙을 기록한다.
- docs/VERIFICATION.md: 실제 실행한 검증과 결과, 실패·미실행 항목을 기록한다.
- README.md: 로컬 준비물, 실행 방법, 샘플 진행 방법, 오프라인 패키지 생성 방법을 설명한다.

최종 보고는 다음 순서로 한다.
1. 이번에 구현한 기능
2. 주요 생성·수정 파일
3. 내가 직접 실행해 볼 명령과 순서
4. 실제 검증 결과
5. 남은 제약과 미구현 범위
6. 다음 단계의 권장 작업

샘플과 공통 구조 검증을 마친 상태를 ‘상용 플랫폼 완성’이나 ‘판매 준비 완료’로 표현하지 않는다. 이번 완료 범위는 공통 플랫폼의 기본 흐름과 동일 게임 원본의 온라인·오프라인 배포 가능성을 검증한 상태다.

이제 현재 작업 폴더를 확인하고 위 범위의 구현을 시작해 줘.
